Целевая аудитория и проблема

Кто именно и в какой момент

Приоритетный сегмент

Ученики 9 класса школ, где в 10-е классы идёт индивидуальный отбор по профилям, и их родители. Пилотный контур — школы Республики Татарстан.

Не «школьники вообще»: сценарий существует только там, где у школы есть несколько профилей и заявление подаётся к конкретному сроку.

Почему не 11 класс. В 11 классе набор предметов уже определён профилем. Решение, которое можно изменить, принимается в 9-м — там и точка воздействия.

Формулировка проблемы

Ученик 9 класса в ситуации записи в профильный 10 класс хочет выбрать профиль, не потеряв интересные ему специальности, но сталкивается с тем, что связь «профиль → ЕГЭ → направление подготовки» нигде не собрана вместе, из-за чего выбирает по сверстникам и нагрузке, а цену решения узнаёт в 11 классе, когда менять поздно.

Текущий и будущий процесс

As Is → To Be

Как происходит сейчас
  • Школа объявляет список профилей и условия отбора в чате или на сайте.
  • Ученик сопоставляет профиль с будущей специальностью сам: сайты вузов, перечни испытаний, форумы.
  • Чаще сопоставление не происходит вовсе — решение принимается по сверстникам и нагрузке.
  • Родитель узнаёт о последствиях, когда в 11 классе выясняется, что нужного ЕГЭ нет.
  • Школа не видит, какие запросы класса её набор профилей не закрывает.

Время: часы разрозненного поиска или ноль. Результат: решение без информации.

Как будет
  • Ученик открывает бота в MAX по коду класса — профили его школы подтягиваются автоматически.
  • Отмечает интересные направления и получает сравнение всех профилей с объяснением потерь.
  • Видит минимальное дополнение: какой предмет вернёт закрывшиеся направления.
  • Карточка разбора уходит в чат — её видит родитель; к сроку приходит напоминание.
  • Школа получает обезличенный агрегат и основание для решения об элективе.

Время: 3–5 минут. Результат: решение, которое ученик может объяснить.

Профиль 106 / 15
Решение и основной сценарий

Что видит ученик

Что в чате, а что в мини-приложении

Чат-бот: вход, код класса, исходное намерение, карточка разбора, напоминание о сроке. Короткие шаги и уведомления — там, где пользователь уже находится.

Мини-приложение: каталог из 32 направлений с поиском, сравнение пяти профилей, пересчёт по добранным предметам. Список и сравнение требуют отдельного экрана.

Ключевая механика

Продукт отвечает не «куда тебе пойти», а «что ты теряешь и что это вернёт». Каждое закрытое направление показано с причиной: какого именно предмета не хватает.

Как считается

Направление доступно, если профиль закрывает все обязательные предметы испытаний и хотя бы один предмет из списка, который выбирает вуз. Отсюда три состояния, а не «да/нет»: вуз вправе выбрать предмет, которого у ученика нет.

Минимальное дополнение

Перебором наборов из одного и двух предметов находим самый дешёвый способ вернуть закрывшиеся направления. Для технологического профиля это обществознание и иностранный язык — они возвращают юриспруденцию и языкознание.

Доли считаются точной арифметикой (обыкновенные дроби), проценты округляются, а не усекаются. Ядро расчёта не зависит от веба и покрыто тестами.

Метрики пилота

  • Доля завершивших сценарий от числа девятиклассников класса — целевое значение ≥ 60 %.
  • Доля изменивших первоначальный выбор профиля после расчёта — прокси-метрика осведомлённости; фиксируется до и после.
  • Среднее число закрывающихся направлений при первоначальном и при итоговом выборе.
  • Доля дошедших до карточки в чате — показатель того, что разбор доходит до родителя.
  • Доля подавших заявление в срок среди получивших напоминание.
  • Число «непокрытых» запросов класса — вход для управленческого решения школы.

Все метрики считаются по обезличенным событиям продукта. Гипотеза: если ученик увидит цену выбора до подачи заявления, доля решений, принятых без информации, снизится.

Профиль 109 / 15
Архитектура

Два сервиса, одна точка правды

api — FastAPI, Python 3.11

Справочники, расчётное ядро, анкеты, обезличенный агрегат, очередь исходящих сообщений, раздача мини-приложения. Хранилище — SQLite на томе.

bot — Python 3.11

Диалог в MAX через Bot API (длинный опрос), запуск мини-приложения, доставка карточек и напоминаний. Своего состояния не хранит и слушающих портов не открывает.

мини-приложение — React 18 + Vite

Каталог направлений, сравнение профилей, экран классного руководителя. Собирается в образ api и раздаётся по HTTPS.

Решения, которые держат систему

  • Очередь вместо входящего порта. Мини-приложение просит API отправить карточку, API кладёт её в очередь, бот забирает и подтверждает доставку. Перезапуск бота не теряет сообщений, напоминание переживает рестарт.
  • Бот без состояния. Владелец данных — API, поэтому начатый сценарий продолжается после перезапуска контейнера.
  • Платформенные детали MAX изолированы в одном модуле-адаптере: изменения в API платформы правятся в одном файле.
  • Тексты сообщений живут в API — одна точка правды для формулировок.

Запуск всех локальных компонентов — одной командой docker compose up --build. Отдельный профиль поднимает стенд-эмулятор Bot API MAX: сквозной сценарий проходится без доступа к платформе.

Пометка о происхождении данных отдаётся в каждом ответе API и видна пользователю в интерфейсе и в карточке. Мы не имитируем интеграции, которых нет.

Персональные данные

Пользователи — несовершеннолетние, поэтому MVP не собирает ФИО, контакты, оценки и возраст. Хранятся идентификатор пользователя MAX, код класса, отмеченные направления и выбранный профиль.

Доступ ученика к своей анкете — по подписанному токену с ограниченным сроком; доступ школы — по отдельному коду куратора, токен привязан к конкретному классу.

Агрегат для школы обезличен

Разрезы открываются только начиная с пяти заполненных анкет в классе: по агрегату нельзя восстановить ответ конкретного ученика. Порог настраивается.

Генеративные модели не используются: расчёт детерминированный, объяснимый и воспроизводимый — это принципиально для сценария, влияющего на решение семьи.

Профиль 1011 / 15
Потенциал масштабирования

Что переносится без изменений, а что придётся адаптировать

Ядро продукта — не меняется
  • Модель «набор углублённых предметов → допустимые испытания → множество направлений».
  • Движок покрытия и минимального дополнения, три состояния доступности.
  • Сценарий: код класса → выбор → сравнение → карточка в чат.
Переменная часть — адаптируется
  • Справочник профилей и сроков конкретной школы.
  • Региональный порядок индивидуального отбора.
  • Перечень вступительных испытаний — обновляется ежегодно.

Порядок тиражирования

1. Один класс пилотной школы→ 2. Все девятые классы школы→ 3. Муниципалитет: школы с индивидуальным отбором→ 4. Регион — через институт развития образования

Куда в первую очередь. В школы того же региона: меняется только справочник профилей и сроков, код не трогается. Канал — классные руководители в MAX, где чат класса уже есть.

Смежный контекст — та же задача, другой справочник. Выбор специальности в колледже, предпрофильная подготовка в 8 классе. Меняется справочник, не логика.

Риски масштабирования: ежегодное изменение перечня испытаний (нужен владелец обновления), разнородность региональных порядков отбора, зависимость наполнения от школы — поэтому куратор школы обязателен в модели внедрения.

Сценарий пилотного запуска

Первый запуск: одна школа, одна параллель

Где

Одна школа Республики Татарстан с несколькими профилями в 10 классе. Две параллели 9 класса, около 50 учеников.

Когда

С февраля, за 8–10 недель до срока подачи заявления на индивидуальный отбор.

Кто владеет процессом

Заместитель директора по учебной работе — вводит профили и срок. Классные руководители — раздают коды классов.

Как встраивается в существующий процесс

  • Точка входа — родительское собрание и чат класса в MAX: там же, где школа уже объявляет профили.
  • Классный руководитель отправляет код класса в чат; ученик открывает бота.
  • Перед собранием завуч смотрит агрегат и приносит на него разговор с родителями.
  • Ничего не требуется устанавливать: MAX уже установлен у участников процесса.

Что нужно для старта и что дальше

  • Данные: профили школы, сроки, коды классов; выгрузка перечня вступительных испытаний.
  • Ресурсы: сервер с HTTPS, токен чат-бота, 1–2 часа куратора школы на ввод данных.
  • Согласования: информирование родителей о том, какие данные собираются.
  • После пилота: при доле завершивших ≥ 60 % и хотя бы одном решении школы на данных — тиражирование на муниципалитет и автоматизация ввода профилей.
Профиль 1013 / 15
Ограничения, риски и допущения

Что мы знаем о границах решения

Допущения

  • Формально ЕГЭ можно сдавать по любому предмету. Модель считает предмет закрытым, если он не изучается углублённо и не добран.
  • Допущение показано пользователю, и его можно снять: чипы «готов добрать предмет» пересчитывают все профили.

Ограничения MVP

  • Справочник испытаний модельный; данные школ демонстрационные.
  • Валидация параметров запуска мини-приложения MAX не реализована — доступ по подписанному токену из бота.
  • Тип кнопки запуска мини-приложения вынесен в настройку и сверяется с документацией платформы.
  • SQLite рассчитан на класс и школу; для региона — перенос на PostgreSQL без смены логики.

Риски и что делаем

  • Устаревание справочника. Версия и дата актуальности видны пользователю; владелец обновления назначается на этапе пилота.
  • Школа не введёт данные. Куратор — обязательная роль модели внедрения, без неё запуск не начинается.
  • Ложная точность. Продукт отделяет факт, расчёт и рекомендацию и прямо пишет, что не заменяет правила приёма вуза и решение школы.
  • Чувствительные ситуации адресуются классному руководителю: продукт не даёт психологических заключений.
