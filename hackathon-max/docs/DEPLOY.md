# Развёртывание: где разместить и как получить HTTPS

## Что вообще нужно хостить

| Компонент | Нужен ли публичный адрес |
|---|---|
| `bot` | **Нет.** Бот работает длинным опросом: он сам ходит в Bot API MAX, входящих соединений не принимает и портов не открывает |
| `api` + мини-приложение | **Да, обязательно по HTTPS.** Мини-приложение в MAX открывается только по защищённому соединению |

То есть хостинг нужен ровно под один сервис — тот, что раздаёт мини-приложение
и REST API. Это сильно упрощает задачу: подойдёт любая машина с публичным
IP, Docker и открытыми портами 80 и 443.

## Требования к площадке

1. Docker с плагином Compose.
2. Открытые порты 80 и 443 (80 нужен для выпуска сертификата).
3. Доступность из России — решение проверяет российское жюри.
4. Работа без присмотра в течение всего периода проверки.

Хватает самого маленького тарифа: 1 ядро, 1 ГБ памяти, 10 ГБ диска.
Нагрузка пилота — десятки анкет в классе, база SQLite.

## Способ 1. Свой домен — рекомендуется

Подходит любой российский провайдер VPS с Docker: Timeweb Cloud, Selectel,
REG.RU, Beget и подобные. Порядок цен на минимальный тариф — несколько сотен
рублей в месяц; уточняйте у провайдера, тарифы меняются. Домен в зоне `.ru`
стоит порядка нескольких сотен рублей в год, подойдёт и бесплатный поддомен,
если провайдер его даёт.

1. Заведите VPS, поставьте Docker.
2. Направьте домен A-записью на IP сервера.
3. Скопируйте решение на сервер и заполните `.env`
   (`MAX_BOT_TOKEN`, `APP_SECRET`, `INTERNAL_KEY`).
4. Запустите:

```bash
SITE_ADDRESS=profil10.example.ru \
PUBLIC_BASE_URL=https://profil10.example.ru \
docker compose -f compose.yaml -f deploy/compose.tls.yaml up -d --build
```

Caddy сам получит сертификат Let's Encrypt при первом запуске и будет его
продлевать. Проверка: `https://profil10.example.ru/api/health` должен вернуть
`{"status":"ok", ...}`.

**Почему так, а не вручную.** Сертификат, его продление и редирект с HTTP
берёт на себя обратный прокси — руками ничего выпускать не нужно, и на
проверке нечему протухнуть.

## Способ 2. Без домена — туннель Cloudflare

Годится, когда покупать домен не хочется, а адрес нужен сейчас.

```bash
docker compose -f compose.yaml -f deploy/compose.tunnel.yaml up -d --build
docker compose -f compose.yaml -f deploy/compose.tunnel.yaml logs tunnel | grep trycloudflare
```

В логах появится адрес вида `https://<случайное-имя>.trycloudflare.com`.
Его нужно положить в `PUBLIC_BASE_URL` и перезапустить `api`:

```bash
echo "PUBLIC_BASE_URL=https://<полученный-адрес>" >> .env
docker compose -f compose.yaml -f deploy/compose.tunnel.yaml up -d api
```

**Оговорка, которую важно понимать.** Такой адрес живёт, пока запущен
туннель, и при перезапуске меняется. Если контейнер перезапустится во время
проверки, ссылка в презентации перестанет работать — а это риск получить
ноль по критерию допуска. Для сдачи надёжнее способ 1.

## Куда подставляется адрес

`PUBLIC_BASE_URL` — единственное место. Из него бот строит ссылку на
мини-приложение, которую кладёт в кнопку. На служебный слайд презентации
идут:

* ссылка на чат-бота в MAX;
* `PUBLIC_BASE_URL` + `/app/` — мини-приложение;
* `PUBLIC_BASE_URL` + `/api` — API, `/docs` — его описание.

## Проверка после развёртывания

```bash
API_BASE_URL=https://ваш-адрес bash tools/check_all.sh
```

Скрипт дождётся готовности API и прогонит тесты, проверки контракта и
сквозной сценарий. Для сценария нужен стенд-эмулятор MAX (профиль `demo`) —
на боевом сервере его не поднимают, там сценарий проверяется вручную через
настоящего бота в MAX.

## Чего в этой инструкции не проверено

Выпуск сертификата, работа домена и туннеля из среды разработки не
проверялись: у неё нет ни публичного адреса, ни доступа к реестру образов.
Конфигурации написаны по штатной схеме Caddy и cloudflared, но первый запуск
на сервере нужно проделать заранее, а не в день сдачи.
